# Plan de release v0.1.1

> **Documento historico y reemplazado. No ejecutar sus comandos, gates, tags, pasos de publicacion ni rollback.** Registra la preparacion de `v0.1.1`, no una release pendiente. Para operar releases use exclusivamente [`../releases.md`](../releases.md), y para el trabajo actual de inventario y SQLite consulte el [plan vigente](./measured-presentations-inventory-cost-corrections.md).

**Estado registrado el 6 de octubre de 2026:** cambios de codigo, pruebas, workflow, documentacion y version `0.1.1` implementados en el worktree de `feat/v0.1.1-updater-fixes`. En ese momento quedaban como gates operativos integrar la rama, ejecutar `mode=validate` en GitHub Actions, probar el AppImage en Mesa reciente, autorizar la publicacion y completar la matriz real `v0.1.0 -> v0.1.1`.

## Objetivo

Publicar `v0.1.1` como la primera actualizacion real de Linea POS y corregir tres problemas detectados al probar `v0.1.0`:

- Permitir actualizaciones firmadas para instalaciones Linux AppImage, `.deb` y `.rpm`.
- Corregir el AppImage que falla en sistemas con Mesa reciente por incluir bibliotecas Wayland incompatibles.
- Permitir que `pnpm tauri dev` inicie sin requerir la configuracion protegida del updater usada por releases.

La release debe conservar el identificador `com.beto98.pos-tauri`, los datos de usuario y las garantias de publicacion atomica existentes.

## Baseline confirmado de v0.1.0

- `v0.1.0` es una release publica e inmutable y no debe modificarse ni reutilizarse.
- La version actual es `0.1.0` en `package.json`, `src-tauri/Cargo.toml` y `src-tauri/tauri.conf.json`.
- El plugin instalado es `tauri-plugin-updater 2.12.0` y distingue en ejecucion AppImage, DEB y RPM.
- El manifiesto actual solo publica `linux-x86_64` para AppImage y `windows-x86_64` para NSIS.
- Los paquetes `.deb` y `.rpm` actuales no tienen una firma `.sig` publicada.
- `pnpm tauri dev` registra el updater sin `plugins.updater`; Tauri intenta deserializar `null` y aborta durante el setup.
- El AppImage incluye `libwayland-*.so*` de Ubuntu. En hosts con Mesa 25 o 26 puede fallar con `EGL_BAD_PARAMETER`.
- `LD_PRELOAD=/usr/lib/libwayland-client.so.0` confirma que la biblioteca incluida en el AppImage es la causa del fallo.

## Decisiones

- AppImage, DEB y RPM seran canales autoactualizables independientes en Linux.
- NSIS continuara como canal autoactualizable en Windows.
- MSI seguira siendo un instalador manual.
- Cada formato tendra su propia entrada y firma en `latest.json`; no se usara una entrada Linux generica que pueda entregar el formato equivocado.
- La clave privada permanecera exclusivamente en los secrets del environment `release`.
- La clave publica y el endpoint continuaran entrando mediante el overlay efimero de release.
- El updater solo se registrara cuando exista una configuracion `plugins.updater` valida. Desarrollo sin overlay no intentara inicializarlo.
- El AppImage se saneara antes de su firma final. Nunca se conservara una firma creada antes de modificar sus bytes.
- Las migraciones `001` a `008` se consideran inmutables desde `v0.1.0`.

## Etapa 1: Corregir el arranque de desarrollo

Modificar `src-tauri/src/lib.rs` para registrar `tauri-plugin-updater` solamente cuando `app.config().plugins` contenga `updater` como un objeto de configuracion.

El comportamiento debe ser:

- `pnpm tauri dev` usa la configuracion base, omite el updater y termina el setup normalmente.
- Un build de release con el overlay efimero encuentra `plugins.updater`, registra el plugin y conserva toda la funcionalidad actual.
- Una configuracion `updater: null` no provoca un panic; se trata como updater no configurado.
- Los errores reales al registrar un updater configurado continuan abortando el setup. No deben ocultarse.

Extraer la decision a una funcion pequena que pueda probarse con configuraciones serializadas sin iniciar una ventana Tauri.

No agregar una clave falsa ni un endpoint de prueba a `tauri.conf.json`. La comprobacion automatica de actualizaciones no forma parte del modo desarrollo.

Actualizar tambien `src/api/updater.ts`, `UpdateController` y su contexto para que el frontend conozca que el updater esta deshabilitado bajo `import.meta.env.DEV`. En ese modo no debe invocar comandos de un plugin ausente ni mostrar la accion manual `Buscar actualizaciones`. Los builds de produccion deben conservar la interfaz actual sin depender de esta bandera para su seguridad.

### Pruebas

- Configuracion sin `plugins.updater`: el updater no se registra.
- Configuracion con `plugins.updater: null`: el updater no se registra.
- Configuracion con un objeto updater: el updater se considera configurado.
- El overlay generado por `scripts/release-config.mjs` sigue produciendo un objeto con `pubkey` y `endpoints`.
- En modo desarrollo no se llama `check()` y no se ofrece la consulta manual.
- En modo produccion el controlador conserva la comprobacion inicial y manual.
- Ejecutar manualmente `pnpm tauri dev` y confirmar que abre la aplicacion sin el panic de deserializacion.

### Resultado esperado

El desarrollo local no depende de variables o claves de release, mientras que los instaladores publicados conservan el updater.

## Etapa 2: Sanear el AppImage

Agregar un script de build dedicado que reciba el AppImage generado y:

1. Trabaje en un directorio temporal con limpieza garantizada mediante `trap` o su equivalente.
2. Extraiga el AppImage sin ejecutar Linea POS.
3. Elimine todas las coincidencias de estas bibliotecas dentro del AppDir:

```text
libwayland-client.so*
libwayland-cursor.so*
libwayland-egl.so*
libwayland-server.so*
```

4. Falle si no encuentra `libwayland-client.so*`, porque eso indicaria que cambio el empaquetado esperado y el saneamiento dejo de verificarse.
5. Regenere el AppImage mediante el `linuxdeploy-plugin-appimage.AppImage` descargado por el bundler de Tauri.
6. Reemplace el artefacto original conservando exactamente su nombre y permisos ejecutables.
7. Extraiga o inspeccione el resultado final y falle si queda cualquier `libwayland-*.so*` prohibida.

El script no debe modificar `.deb` ni `.rpm`; esos paquetes usan las bibliotecas administradas por el sistema.

Integrar el saneamiento en el job `linux` de `.github/workflows/release.yml` inmediatamente despues de `tauri-action` y antes de firmar o subir artefactos.

### Firma del AppImage

- Eliminar la firma producida para los bytes anteriores al saneamiento.
- Firmar nuevamente el AppImage final con `pnpm tauri signer sign`.
- Verificar la nueva firma antes de subir el artifact temporal.
- No imprimir la clave privada, su ruta ni su contrasena.

### Pruebas

- Probar la seleccion y eliminacion de las cuatro familias de bibliotecas en un AppDir fixture.
- Rechazar un AppDir que no contenga la biblioteca principal esperada.
- Rechazar un resultado que conserve una biblioteca prohibida.
- Agregar un contrato del workflow que exija el orden `build -> saneamiento -> firma -> upload`.

### Resultado esperado

El AppImage de `v0.1.1` inicia en Mesa reciente sin `LD_PRELOAD` y su firma corresponde a los bytes publicados.

## Etapa 3: Firmar DEB y RPM

Despues de generar y sanear los bundles Linux:

- Localizar exactamente un `.deb` y exactamente un `.rpm`.
- Rechazar cero coincidencias, multiples coincidencias o nombres inseguros.
- Generar `*.deb.sig` y `*.rpm.sig` con `pnpm tauri signer sign`.
- Mantener los secrets de firma limitados al job protegido `linux` y solamente despues de compilar el frontend sin privilegios.
- Incluir ambas firmas en `actions/upload-artifact`.

No depender de que `createUpdaterArtifacts` genere estas firmas automaticamente. El workflow debe firmar explicitamente los paquetes nativos que publicara el manifiesto.

### Pruebas

- El job Linux exige los tres instaladores y sus tres firmas.
- Una firma ausente o vacia detiene la release.
- Una firma correspondiente a otro archivo es rechazada por `minisign`.
- Los secrets no estan disponibles en los pasos de checkout, instalacion de dependencias o build frontend.

### Resultado esperado

AppImage, DEB y RPM tienen firmas independientes y verificables con la misma clave publica ya confiada por `v0.1.0`.

### Compatibilidad N-1

`v0.1.0` ya usa `tauri-plugin-updater 2.12.0`. Ese cliente busca primero la clave especifica de su bundle:

```text
{os}-{arch}-{bundle_type}
```

Por eso una instalacion `.deb` de `v0.1.0` podra seleccionar `linux-x86_64-deb`, y una instalacion RPM podra seleccionar `linux-x86_64-rpm`, aunque el manifiesto de `v0.1.0` todavia no tuviera esas entradas.

### Pruebas

- Generar las cuatro entradas con URLs exactas de la misma release.
- Rechazar una firma intercambiada entre AppImage, DEB o RPM.
- Rechazar una clave generica o inesperada.
- Rechazar ausencia o duplicado de cualquier instalador o firma requerida.
- Rechazar assets adicionales no declarados.
- Verificar codificacion segura de nombres en URLs.

### Resultado esperado

Cada instalacion descarga exclusivamente su propio formato y nunca intenta instalar un AppImage como DEB o RPM.

### Resultado esperado

## Recuperacion y rollback

- Si falla antes de crear el draft, corregir el codigo o la configuracion y crear un nuevo commit; no mover un tag publicado.
- Si falla con un draft existente, conservarlo y reintentar para que el workflow reconcilie el conjunto completo.
- Si cualquier firma o clave de manifiesto no corresponde a su formato, no publicar.
- Si una release ya fue publicada con un defecto, conservarla inmutable, retirarla de `latest` solo si es necesario y preparar `v0.1.2`.
- No sustituir assets de `v0.1.0` ni `v0.1.1` despues de publicarlos.

## Criterios de finalizacion

- `pnpm tauri dev` abre sin configuracion ni secrets de release.
- El modo desarrollo no invoca comandos updater ni muestra una accion que no puede completar.
- El updater sigue registrado en builds creados con el overlay de release.
- El AppImage final no incluye las cuatro familias `libwayland-*.so*` prohibidas.
- AppImage inicia en CachyOS con Mesa reciente sin `LD_PRELOAD`.
- AppImage, DEB, RPM y NSIS tienen firmas verificadas.
- `latest.json` contiene solamente las cuatro claves especificas acordadas.
- Una instalacion nunca recibe un paquete de otro formato.
- MSI permanece fuera del updater.
- El conjunto remoto contiene nueve assets nativos y `latest.json`, sin faltantes ni extras.
- Las pruebas `v0.1.0 -> v0.1.1` pasan en los cuatro canales.
- SQLite y el identificador de aplicacion permanecen estables.
- CI, formato, Clippy, pruebas debug y release terminan correctamente.
- La release se publica atomica e inmutablemente.
